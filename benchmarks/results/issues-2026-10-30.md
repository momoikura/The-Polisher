# Re-run: the same issues a day later (2026-10-30)

The [2026-10-29 benchmark](issues-2026-10-29.md) re-run unchanged after a day of
speed and quality changes, to see what they did. The list was committed before
running ([`issues-2026-10-30.json`](../issues-2026-10-30.json), commit `84b0662`):
the same issues minus [sqlglot#8820](https://github.com/tobymao/sqlglot/issues/8820),
which was closed upstream in between (its fix may now be in the code).

Changes since the first run: targeted tests while polishing (whole suite once at
the end), cached results for the original code, polish caps once objective checks
pass, a 20-minute limit, verifying alongside reconcile, agent playbooks, and
reading screenshots in issues.

## Result

| Same 16 issues | 2026-10-29 | 2026-10-30 re-run |
|---|---|---|
| **Fix proven by its own new tests** | **13** | **12** |
| Single-prompt draft proven | 7 | 7 |
| Status clean or verified | 5 | 8 |
| Median time | 10.8 min | 17.8 min |
| Longest run | 50 min | 26 min |
| Model cost | $0.61 | $0.54 |

The re-run found two bugs, both introduced or exposed by the changes:

1. **Targeted test runs named tests differently.** Given specific test files, pytest
   picked `tests/` as its root in repos that don't pin one (Rich), so it reported
   `test_cells` instead of `tests.test_cells`. Targeted runs then never found the
   new tests (a false "new tests don't pass") and didn't recognise failures that
   already existed. CodePolish spent most of Rich#4239's 22 minutes chasing the
   false failure. Fixed: every pytest run pins `--rootdir`.
2. **The gate threw away a proven fix over a lint error.** On sqlglot#8752 a
   revision made the new tests prove the fix (failing checks 3 → 1), but the one
   left was an unused import, on a check that had passed before, so the rule
   "never break a passing check" rejected it. Fixed: a revision may break a minor
   check (lint, debug leftovers, error wording) when it fixes strictly more checks
   than it breaks; tests, the proof of the fix and the security scan still never.

## Confirmation after both fixes

The five issues those bugs hurt, run once more after fixing them (a confirmation,
not a pre-registered benchmark; raw results in
[`confirm-2026-10-30.jsonl`](confirm-2026-10-30.jsonl)): **all five proven, three clean.**
On sqlglot#8752 the revisions improved without needing the new gate rule this time,
so that run doesn't test the rule directly.

## What it doesn't show

- The confirmation covers only the five issues the bugs hurt; the other eleven were
  not re-run after the fixes. A full re-run would give a clean "after" number.
- One run per issue: run-to-run variation is large (Rich#4238 has taken 19–29 min).
- The 20-minute limit still overshoots (up to 26 min): it stops new revisions, not
  one already under way or the final whole-suite check.
- Runs on 2026-10-30 saved full timelines and are on the app's Runs page.

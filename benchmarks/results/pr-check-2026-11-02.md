# Checking real pull requests, 2026-11-02

ThePolisher can now check someone else's pull request. Its code runs in the sandbox on the commit it branched from, and Muse Wonder writes its own tests against it. Nothing is posted to GitHub.

I ran it on 23 closed pull requests, chosen by a fixed rule before running: the newest 3 merged and newest 3 closed without merging per repo, by people, changing Python outside the tests, in Rich, jsonschema, humanize and more-itertools ([rule](../select-prs.mjs), [list](../pr-check-2026-11-02.json), [results](pr-check-2026-11-02.jsonl), [retries](pr-check-retry-2026-11-02.jsonl)). jsonschema only had 2 merged PRs that fit.

## The verdicts

| Verdict | Merged (11) | Closed, not merged (12) |
| --- | --- | --- |
| Its tests show it works | 3 | 11 |
| Breaks tests | 0 | 1 |
| Nothing breaks, but it adds no tests | 4 | 0 |
| Its tests pass without it too | 3 | 0 |
| Its own tests fail | 1 | 0 |

Total cost $1.18. Most checks took 1 to 2.5 minutes.

**These verdicts do not predict what gets merged.** Closed PRs scored better than merged ones. Maintainers close working PRs for many reasons, and they often merge small changes and refactors with no new tests. The check answers a narrower question: what does this code do when it runs? It doesn't tell a maintainer whether to want the change.

## What Muse Wonder found

**A real bug, in a merged PR.** On [Rich#4076](https://github.com/Textualize/rich/pull/4076), Muse Wonder's test passed on the original code and failed with the PR. I re-ran the same check in the sandbox on three commits:

| Commit | `AnsiDecoder().decode("foo\r\nbar\r\nbaz")` |
| --- | --- |
| Before the PR | `['foo', 'bar', 'baz']` |
| With the PR | `['', '', 'baz']` |
| Rich's main branch, `9d8f9a3` | `['', '', 'baz']` |

Text on lines ending in CRLF is lost. This isn't a new discovery: a person reported it as [Rich#4090](https://github.com/Textualize/rich/issues/4090) ten days after the merge, and it's still open. The check flagged it on the PR. [See that run](https://thepolisher.pages.dev/runs/b1eb802c-5e3b-42f5-8ba5-7859e88d0117).

**It doesn't catch this every time.** Muse Wonder writes different tests on each run. When I ran the same PR again through the app, its tests still went after CRLF and went 0 of 3, but all three also failed on the original code, so that run didn't single out the PR. The original code can fail a test for a different reason, so the page now says only that it "also fails on the original code, possibly for a different reason".

**It's noisy.** Many tests that failed on both the original code and the PR are wrong guesses about behaviour, like expecting a function argument that doesn't exist. The page and the comment label these. Of the 23 PRs, 3 had a Muse Wonder test that passed on the original code and failed with the PR:

| PR | Result |
| --- | --- |
| Rich#4076, merged | The real bug above. |
| Rich#4077, merged | A behaviour change: `FileProxy.isatty()` now raises when the wrapped file has no `isatty`, where it returned `False` before. I don't know if the maintainer would call that a bug. |
| Rich#4146, closed | Not looked into. This PR also breaks other tests. |

## After improving Muse Wonder

I gave it the changed code in full, not just the diff, more tokens, and the aim of finding what the change broke, then ran the same 23 PRs again ([list](../pr-check-v2-2026-11-02.json), [results](pr-check-v2-2026-11-02.jsonl)).

| | Before | After |
| --- | --- | --- |
| PRs where it produced no tests | 1 | 0 |
| Tests that pass on the original code and fail with the PR | 5, on 3 PRs | 11, on 5 PRs |
| Tests that fail on both | 22 of 66 (33%) | 30 of 69 (43%) |
| Total cost | $1.18 | $2.00 |

**It flags more, and it isn't less noisy.** I kept it because finding what a change broke is the point, and changed the page instead: those tests come first, and tests that fail both ways fold into a count. The two PRs it newly flagged, jsonschema#1482 and more-itertools#1334, are behaviour changes I haven't confirmed as bugs.

The skipped run also had a real cause: with 5,000 tokens, Muse Wonder could spend them all thinking and reply with nothing. That reply went uncharged. Both are fixed.

**How often does it catch Rich#4076?** On 5 more runs of that PR ([list](../detect-4076-2026-11-02.json), [results](detect-4076-2026-11-02.jsonl)), 4 flagged tests that pass on the original code and fail with the PR. Only 1 of those was the exact CRLF text loss. The others found related changes in the same PR, like `\r` and `\v` no longer splitting lines, which may be intended.

## Letting Muse Wonder fix its own wrong guesses

A test that fails on the original code too is often a wrong guess, like an argument that doesn't exist. So Muse Wonder now gets one chance to fix those tests, or to keep any it's sure about, and they run again. Same 23 PRs ([list](../pr-check-v3-2026-11-02.json), [results](pr-check-v3-2026-11-02.jsonl)).

| | Before | After |
| --- | --- | --- |
| Tests that fail on both the original code and the PR | 30 of 69 (43%) | **7 of 65 (11%)** |
| Tests that pass on the original code and fail with the PR | 11, on 5 PRs | 13, on 6 PRs |
| Total cost | $2.00 | $2.53 |

**The noise dropped by about four times, for 26% more cost.** It still flagged the CRLF bug on Rich#4076: `Text.from_ansi("Hello\r\nWorld\r\n")` gives `"\n\n"`.

### How often its flags are real

"Passes on the original code and fails with the PR" is a fact about behaviour. Whether that behaviour change is a bug is a judgement, and I've only checked one.

| PR | Flagged in | What I know |
| --- | --- | --- |
| Rich#4076, merged | every version | A real bug, reproduced and still open as Rich#4090 |
| Rich#4077, merged | every version | A behaviour change: `isatty()` now raises where it returned `False`. Not confirmed as a bug |
| Rich#4146, closed | every version | Not looked into. The PR also breaks other tests |
| jsonschema#1482, merged | the last two | Not confirmed |
| more-itertools#1334, merged | the last two | Not confirmed |
| Rich#4079, merged | the last one | Not confirmed |

So of the 6 PRs it flags, 1 is a confirmed bug, and none has been shown to be a false alarm. Checking the other five would take a person reading each one, which I haven't done.

## Then fixing it

I gave Rich#4090 to the full pipeline ([list](../rich-4090-2026-11-02.json), [results](rich-4090-2026-11-02.jsonl), [the run](https://thepolisher.pages.dev/runs/09e2e317-527f-44dd-8b38-52723ce52230)). It was clean and proven, with 954 of 987 tests passing and no new failures, in 238 seconds for $0.036. Muse Wonder's tests on that fix passed 2 of 3, and its one failure also fails on the original code. No PR was opened: Rich already has two open PRs for this.

## Limits

- **Rich#4079, merged, shows "its own tests fail".** I didn't confirm why. The sandbox installs the newest dependencies, so a version change is the likely cause, and the page says so.
- **Only Python files are applied.** A PR's data files and removed files aren't, and the result lists them. A PR that depends on them can look worse than it is.
- **23 PRs in 4 repos is a small sample.** Results may not carry over to other projects.
